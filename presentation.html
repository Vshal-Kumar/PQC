Problem Statement & Motivation

Addressing the impending quantum threat and resource constraints on embedded nodes.

⚠️ The Quantum Threat

• Vulnerability of Classical Crypto: Shor's algorithm breaks RSA and ECC.

• "Harvest Now, Decrypt Later": Adversaries store today's encrypted network traffic to decrypt once quantum hardware matures.

• NIST Standardization: Mandates migration to ML-KEM (FIPS 203) and ML-DSA (FIPS 204).

🧩 Embedded Performance Bottlenecks

• Large Key Sizes: ML-KEM-768 PK = 1,184 B; ML-DSA-65 signature = 3,293 B (vs classical ECC 64 B).

• Heavy Lattice Math: Polynomial vector multiplication and Number Theoretic Transforms (NTT) strain low-power CPUs.

• Resource Constraints: Unoptimized PQC degrades connection times on ARM edge hardware.

System Architecture & Handshake Flow

4-Way PQC UDP protocol sequence and decoupled POSIX IPC server engine.

🔄 4-Way PQC Handshake Protocol

1. PKT_CLIENT_HELLO: Client ──► Server: (KEM_PK_c, DSA_PK_c, Nonce_c)
2. PKT_SERVER_HELLO: Server ──► Client: (DSA_PK_s, KEM_CT, SessionID, Nonce_s, Sig_s)
3. PKT_CLIENT_AUTH: Client ──► Server: (Sig_c over transcript)
4. PKT_ACK & Active: Key derived via SHAKE256 KDF. AEAD active.

🖥️ Decoupled POSIX IPC Server Engine

• server Daemon: Listens on UDP port 9877 using io_uring async I/O.
• server_rx Console: Connects via /tmp/pqc_rx.sock UNIX socket.
• server_tx Console: Connects via /tmp/pqc_tx.sock UNIX socket.
• Zero Display Latency: Logging decoupled from network routing.

💡 Hybrid Operational Security

Combines forward-secret ephemeral ML-KEM-768 key exchange with ML-DSA-65 digital signature authentication. Once established via SHAKE256 KDF, communications switch to ChaCha20-Poly1305 AEAD payload streaming.

Formal Security Verification (ProVerif)

Applied Pi-Calculus mathematical proofs under Dolev-Yao attacker model.

Security Property Result ProVerif Formal Query
Session Key Secrecy VERIFIED query attacker(session_key_secret)
Client Payload Secrecy VERIFIED query attacker(client_data)
Server Payload Secrecy VERIFIED query attacker(server_data)
Injective Mutual Auth VERIFIED inj-event(server_accepts) ==> client_initiates
Perfect Forward Secrecy VERIFIED Phase 1 long-term key leak query
🔍 Verification Highlights

• Dolev-Yao Attacker Model: Active adversary controls network packets.
• Phase-Based PFS Proof: Phase 0 honest sessions; Phase 1 long-term key leak. Phase 0 session keys remain secret.
• Attack Immunity: Resistant to KEM substitution, UKS attacks, and reflection.

SIMD Hardware Acceleration & Toolchain

Microarchitectural vectorization and isolated arm64_ref build environment.

⚡ SIMD Acceleration Pipeline

• x86_64 Server: AVX2 256-bit + BMI2 instruction set. 3.2x Speedup.
• ARM64 Client: 128-bit NEON SIMD vector registers. 2.8x Speedup.
• ARM32 Client: NEON + VFPv4 hard-float execution. 2.1x Speedup.

🛠️ Portable arm64_ref Toolchain

• The Challenge: Cross-compiling ARM binaries on x86 host leads to OpenSSL static library architecture mismatches (ELFCLASS64).
• The Solution: Self-contained reference layout (arm64_ref/) housing ARM64 pre-compiled static libraries (libcrypto.a, liboqs.a).
